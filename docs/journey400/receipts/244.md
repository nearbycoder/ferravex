## Semantics and exact mutation contract

Each operation copies authored weights into `[u32; N]` scratch and starts a fresh pool. Selection scans cumulative weights in original index order, then removes the selected index's entire weight from scratch. Distinctness is table-index identity, even if the caller maps multiple indices to the same reward value. Zero weights cannot be selected. Authored weights/total never change.

Preflight precedence is request, capacity, then sample-budget ceiling (roll only):

1. `requested > 256` returns `RequestTooLarge`.
2. `out.len() < min(requested, positive_weight_entry_count)` returns `OutputTooSmall`, even if the proposed sample budget/tickets would only produce a shorter prefix. A buffer shorter than the request is sufficient when the pool has fewer eligible entries.
3. `sample_budget > 4096` returns `SampleBudgetTooLarge`, including for a zero request.

Every preflight error leaves the complete output and RNG state unchanged; no RNG outputs are consumed. A nonzero request with an empty output errors, since validated tables always have a positive entry. Zero requested with valid budget completes without mutation/consumption. Zero budget is valid: nonzero requested yields an empty `SampleBudgetExhausted` prefix, without consuming RNG or touching output.

For rolling, each attempt consumes exactly one existing SplitMix64 output; take its upper 32 bits `x`. With remaining u32 total `W > 0`, reject `x < (2^32 mod W)`; otherwise select ticket `x % W`. Both accepted and rejected attempts consume one sample-budget unit. Even W=1 consumes one output for an accepted draw. There is no duplicate-draw retry, unbounded entropy retry or biased fallback.

For independent uniform input words, the accepted domain contains equally many representatives of each residue modulo W, so conditional on that next draw succeeding, index i has probability `remaining_weight[i] / W`. Finite global budgets can censor prefixes depending on preceding selections; the distribution of full requests conditioned on completion is not claimed to preserve those sequential probabilities. SplitMix64 itself is deterministic gameplay variety; no independent/security/matchmaking entropy claim.

For the deterministic ticket operation, each consumed u32 ticket is reduced modulo the remaining total. Arbitrary uniform u32 tickets are **not** claimed to map without modulo bias. Independent uniform tickets in each current range give sequential weight-proportional choices. Tickets depend on table weights/order; saved indices still depend on order. Stable reward identities/content-version coordination remain host-owned; no existing record format changes here.

On every successful return, only `out[..written]` is changed. Tail values are untouched. Reported `samples_used` is exact, including rejected RNG outputs, or the number of deterministic tickets read. No inputs are consumed after completion/pool exhaustion. Stop precedence: exact requested count gives `Complete`; otherwise an empty positive pool gives `TableExhausted`; otherwise input exhaustion gives `SampleBudgetExhausted` or `TicketsExhausted`. Thus a completed request that also used its last budget/ticket still reports `Complete`.

Input exhaustion is an accepted partial-prefix result, never a rollback: consumed RNG stays consumed, rejected attempts have no output writes, accepted indices remain in the prefix. A subsequent call starts the full pool and must not be concatenated as a continuation. Keep one result for menu redraws; use the prefix as a shorter offer set if your policy allows it. Reset/replay by reconstructing the run RNG from its seed and replaying the same calls, not by pretending consumed samples were restored.

## Storage, work and allocation evidence

- No heap allocation, floating weights, callbacks, wall clocks or platform I/O in either production draw path. Scratch is N u32 weights (at most 1024 bytes) plus scalar bookkeeping; caller owns the output.
- Rolling has at most 4096 attempts, at most 256 accepted writes, and at most N weight visits for each accepted draw, plus bounded preflight/copy. Complexity: `O(N + sample_budget + N * min(requested, positive_entries))`; N and requested are at most 256.
- Ticket draws consume at most `min(requested, positive_entries, tickets.len()) <= 256` tickets. Long ticket slices are not scanned. Complexity: `O(N * (1 + min(requested, positive_entries, tickets.len())))`.
- Integration tests install a thread-local counting System allocator. A live-counter Box allocation is observed first. Maximum-size seeded rolls and ticket draws, a forced rejection/partial outcome, and a preflight capacity error each measured zero allocation/reallocation calls during the draw. Assertions/allocation for fixture comparison occur outside measurement. Test-only unsafe allocator forwarding is isolated in the integration-test crate; production retains `#![forbid(unsafe_code)]`.
- These checks establish measured native test cases and source bounds, not a stack-size benchmark or cross-platform allocator measurement.
