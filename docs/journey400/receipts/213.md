impl World {

    pub fn prepared_entity_capacity(&self) -> usize;

#[non_exhaustive]
pub enum SpawnError {
    DuplicateComponent(&'static str),
    OutputTooSmall { required: usize, available: usize },
    EntityCapacity { required: usize, prepared: usize },
    ComponentCapacity { component: &'static str, required: usize, prepared: usize },

`SpawnError` implements `Display` and `std::error::Error`. The existing exhaustive
`Error` enum is unchanged. No Clone, Copy, Default or Debug bound is added to
components. A caller using `unwrap` on a batch Result separately needs Debug
for its returned inputs; the recipe instead maps the error explicitly.

## Capacity and preparation semantics

- Budgets count **total sparse indices**, not additional entities, live entities
  or a type's occupied component count. They start at zero and increase
  monotonically to the largest successful explicit preparation request.
  Allocator rounding and ordinary spawn/insert growth never increase budgets.
- Entity preparation reserves the entity-slot Vec and the free-index Vec. It
  does not extend the slot length, create identities, consume the free list,
  change generations or shrink storage. Component preparation independently
  registers the typed storage, reserves its Vec and extends it with empty slots.
  It does not construct, replace or drop component values. Even a zero component
  preparation registers an empty typed storage; an absent type's getter also
  returns zero.
- Requests must fit u32 indices and usize counts: for nonzero capacity,
  `capacity - 1` must fit u32. On the tested 64-bit host the identity ceiling is
  2^32 total slots. Checked arithmetic handles count overflow. On 32-bit targets
  a total length of 2^32 cannot be represented; no new identity layout is added.
- Preparation uses `try_reserve_exact` on Vecs and `try_reserve` on the map.
  Reservation errors, including layout/capacity overflow, become
  `AllocationFailed`; identity failures become `IdentityCapacity` first.
  Reported preparation errors leave budgets, entity identities and values
  unchanged. A prior successful reservation can still enlarge buffer/map
  capacity. New typed storage is inserted only after its Vec preparation succeeds.
- Storage Box allocation uses the ordinary allocator and can panic/abort rather
  than returning an error. Allocator panic/abort and arbitrary user construction
  or Drop are not made infallible, caught or rolled back.
- Budgets and buffers survive despawn/repopulation of the same world. Replacing
  the World resets them. There is no new clear/shrink/reset policy or live cap
  on legacy ordinary spawn.

## Batch preflight, ownership and failure behavior

The fixed-array input transfers ownership without cloning components. All
bundles have the same sealed Bundle type; validation uses task 212's existing
eight-entry stack metadata, never the compatibility Vec API. Empty bundles and
all supported tuple widths zero through eight remain accepted. Filter groups
retain their separate four-clause limit.

Preflight order is duplicate component types, output length, identity arithmetic,
entity budget, then typed-component budgets in bundle order. It validates
duplicates even for N=0. A valid empty batch requires no preparation and returns
zero without registering types or allocating ECS storage. AllocationFailed is
returned by preparation, not by this allocation-free preflight/spawn path.

Batch selection mirrors ordinary spawn: pop free indices in LIFO order, then
append new indices. If new slots are needed, the required budget is existing
slot length plus new slots. Otherwise it is the highest **selected** free index
plus one. Unselected high indices do not force larger budgets; retired indices
still contribute to the sparse high-water mark when appending. A small live
population can therefore still need a large sparse budget.

Every reported batch error returns `(SpawnError, original_array)`. No component
is extracted from that array or dropped by the operation. All existing live
entities/components, generations, slot count, free-list order, registered types,
ECS capacities and every output element remain unchanged. Callers may retry the
same returned array or explicitly drop it. Destructors run when the caller drops
the returned values, and may panic at that later point.

On success exactly N entities are added in input order, output[..N] receives
their handles and Ok(N) is returned. output[N..] is untouched. Output can contain
arbitrary initial handles, including stale/sentinel handles. Reused indices
keep the generation produced by existing despawn semantics; exhausted slots
remain retired. Query iteration retains stable slot order independently of
batch input order.

After successful preflight, the code uses the same private `spawn_validated`
mechanism as ordinary spawn. Prepared bounds ensure no entity/map/component
buffer growth, new storage boxes or metadata allocation. Spawning does not push
free indices. This is an all-or-none guarantee for **reported errors**, not a
panic transaction. Panics/aborts are not caught or rolled back; ordinary unwind
cleanup can drop unconsumed owned input. Construction occurs before the call.
Caller-selected N also determines stack usage and work; there is no hidden
unbounded iterator or additional scratch heap collection.
