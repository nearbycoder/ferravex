## Concrete behavior

`prepare` records SHA-256 hashes of current first-party inputs before the parent generates Rustdoc. `build` consumes existing generated HTML with that snapshot; it never invokes Cargo or builds the site. `search` validates input hashes, generated page inventory, all referenced evidence hashes, the versioned index checksum, and serialized bounds on every call. There is no stale override or cached prior-success state.

Names and qualification come from Rustdoc titles and main headings. Member names come from actual declaration links checked against their anchors. Signatures come from `pre.item-decl` / `h4.code-header`. Source paths come from rendered source-page metadata; rendered source is compared with the checkout (CRLF normalized), and line ranges are validated. Filenames are used only to locate documents. A misleading filename cannot create a symbol. Site `search.json` by itself is deliberately insufficient: its current schema lacks input freshness and isolated declaration evidence.

Results expose:

- `name`, `qualified_path`, `import_path`, `kind`.
- `signature` (at most 640 characters), `signature_truncated`.
- `doc`: repository-relative HTML path, fragment, escaped local file URL.
- `source`: repository-relative Rust path, start/end lines, rendered source path/fragment and escaped local file URL.
- `features`: caller-declared build configuration; rendered portability text when present; `requirements_known: false`. Build flags are **not** claimed to be an individual item's required features. Unknown target remains null.
- `provenance`: Rustdoc format, identity evidence type, page SHA-256; the response also carries index/snapshot hashes, observed Rustdoc versions, and read-time freshness status.

For an associated item such as `demo::Rig3::update`, `qualified_path` names the member and `import_path` is `demo::Rig3`. This avoids suggesting an invalid `use demo::Rig3::update`. Trait declarations, raw identifiers, Unicode names, macros, and documented reexport mirrors are supported. Concrete trait implementations (including foreign implementations inside trait pages), blanket/auto-trait/deref members, fields, and variants are excluded. Module/crate signatures are null when Rustdoc renders no declaration. Redirect/unrecognized/no-first-party-source pages are skipped and counted. This is a declaration search, not an exhaustive Rust name-resolution engine.

`exact` matches a case-insensitive complete name or suffix of qualified components. `fuzzy` ranks exact matches, last-component prefixes, then bounded Levenshtein matches (distance <=2, <=1 for queries shorter than five characters). `auto` returns only exact matches when available and otherwise uses fuzzy lookup. Ties sort by qualified path, kind, document and fragment. No prose search or external fuzzy package is used. Valid zero-match queries succeed. Results include total matches and an explicit truncation flag.

Bounds: 20,000 input/evidence files, 8 MiB per ordinary file, 256 MiB total bytes per input/evidence scan, 64 MiB serialized JSON, 50,000 symbols, nesting/depth 128, local path/name 512 characters, query 160 characters, result limit 1–100, signature 640 characters, availability text 320 characters. Bounds reject excess work instead of publishing a truncated index. Only displayed signatures/availability and requested result counts are intentionally clipped and marked. The stored index references one configuration object instead of duplicating large feature arrays per symbol.

## Exact public interfaces

Python entry points (Path-compatible `root`; returned values are ordinary JSON-compatible dictionaries):

```python
prepare(root, *, packages=(), features=(), all_features=False,
        no_default_features=False, target=None)
build_index(root, docs_root, snapshot)
search_index(root, index, query, *, mode="auto", limit=10)
main(argv=None)
IndexError(code, message)  # ValueError subclass; stable .code field
```

The first three return dictionaries; `prepare` and `build_index` do no writes. `search_index` reads an on-disk index. `main` returns an integer status and prints one JSON response; `--help` is the human-text exception. Helpers beginning with `_` are internal. CLI usage in the module docstring is a first-party recipe; fixture tests exercise the public Python APIs and actual CLI subprocesses.

CLI contract (global `--root` must precede the subcommand):

```text
python3 -B scripts/api-index.py [--root ROOT] prepare
    [-p PACKAGE ...] [--features FEATURES ...] [--all-features]
    [--no-default-features] [--target TARGET] --output NEW_PATH
python3 -B scripts/api-index.py [--root ROOT] build
    --snapshot PATH [--docs target/doc] [--output target/api-index.json]
python3 -B scripts/api-index.py [--root ROOT] search QUERY
    [--index target/api-index.json] [--mode auto|exact|fuzzy] [--limit 10]
```

`-p`/`--package` and `--features` repeat; feature strings retain their Cargo argument meaning. Packages are read from explicit workspace member manifests, including `[lib].name`; default selection includes library packages only. Explicit binary-only selections fail. Output paths must be new, inside the checkout, outside snapshotted source directories, and have an existing parent. Nothing overwrites an existing index/snapshot.

Success: `schema_version: 1`, `status: "ok"`, exit 0. Search additionally returns `query`, `mode`, `results`, `total_matches`, `truncated`, `provenance`. Prepare/build return `command`, `output`, `payload_sha256`; build also returns `symbols` and `skipped_pages`.

Failure: `{"schema_version":1,"status":"error","error":{"code":"...","message":"..."}}`, exit 2, without a traceback or partial result on stdout. Codes include `missing_index`, `stale_index`, `invalid_index`, `invalid_evidence`, `missing_input`, `invalid_path`, `capacity`, `invalid_workspace`, `unknown_package`, `invalid_arguments`, `output_exists`, and `invalid_input` for malformed input/OS failures.

Snapshots use `kind: "ferravex.api-inputs"`; indexes use `kind: "ferravex.api-index"`. Both are schema version 1 and include `payload_sha256` over deterministic sorted compact JSON of the object excluding that field, including a final newline. Their purpose is local integrity/freshness, not a cryptographic trust boundary against a dishonest producer.

## Limits

Future markup may require a parser update and new schema/fixtures where appropriate. Workspace glob/exclude resolution and binary-only APIs are unsupported rather than guessed. Local file URLs are produced; no assumption about a site deployment origin is made. Snapshot timestamps and preserved HTML mtimes are freshness guards, so timestamp resolution/copy behavior can conservatively reject otherwise usable docs.
