## Concrete behavior and compatibility

`step_player_with_settings_detailed` is the single local movement/weapon implementation; `step_player_detailed` supplies default settings, and both legacy bool helpers return exactly its `transitions.fired`. The original public `try_move_player -> Result<(), CharacterError>` delegates to a private helper with identical arithmetic, settings, sanitization, motor call and state writeback. The private helper returns `CharacterStep::jumped` from that actual successful call. No movement, weapon or combat arithmetic is duplicated, and jumps are never inferred from velocity/grounded fields or raw buttons.

Local results report accepted reload start, reload completion, jump and fire. Invalid WeaponSettings return `InvalidWeaponSettings` and preserve the entire player, even a due corpse. A movement error returns the original `CharacterError`, retains the existing sanitized yaw/pitch update, preserves motion/jump and skips all cooldown/reload/ammo work. Errors have no accepted transitions. No checkpoint validation was added to bool/local helpers: raw local ammo/ID values that previously stepped continue to do so. Dead countdown/respawn computations are error-free empty outcomes.

Processing order remains movement/jump, cooldown decrement, reload completion, reload start, fire. Held reload starts only when the actual start condition succeeds; the running reload does not repeatedly start. Completion plus fire in one tick sets both flags in one record. A held reload can legitimately start another reload on a later tick after accepted fire spent a round; that preexisting behavior is preserved. Jump acceptance includes buffered and coyote jumps, including a later tick with no raw jump button. A ceiling can stop the impulse while the jump remains accepted by the motor. Held jump does not fabricate new acceptance.

Match retains the ONE shared motor/combat/rewind loop. New checked calls forward an optional sidecar into it after existing preflight; allocating convenience wrappers pass `None` and retain their original output shape and permissive raw-state behavior. Sidecar records are nonempty accepted aggregates in existing roster order, or ascending ID on the existing explicit safe-spawn path. Input policy, first-input/time precedence, sanitization, custom settings, damage, legacy event order, spawn reservations/deferral, life generation changes and rewind semantics remain unchanged.

Each record has actor ID, **resulting `Match::tick` after the executed tick**, full u64 authority life generation at execution, and the four flags. This tick matches the tick hosts attach to GameEvents, including u32 wrap. It is not an input sequence or historical ShotTime. Life is sampled before later damage resolution; an actor may accept fire/jump and then be killed that tick. Respawn/countdown/deferred-spawn/frozen/disabled-auto-respawn dead actors emit no transition records. Living actors still execute when auto-respawn is disabled. Invalid settings/movement errors emit none. Invalid shot time suppresses only fire exactly as before; movement, jump and reload completion may still be accepted and reported on that tick. Complete original rejection records remain in the original channel.

Sidecar capacity is permanently `MAX_PLAYERS == 16`, with at most one aggregate per actor. It is inline fixed storage rather than a third Vec, so old constructors cannot undersize it. Existing bounded unique-roster preflight proves the push bound; there is no truncation, reallocation or speculative sizing step. Existing `StepCounts` fields, `StepError` variants, `RewindStep`, `GameEvent`, `Player`, bool helpers and public motor signature are unchanged, preserving literals/exhaustive matches. `transition_count` and `transition_capacity` expose separate additive count/capacity information. StepOutput's private in-memory size grows by the inline buffer; it is not a wire/save struct.

Existing capacity, state and safe-spawn policy preflight complete before clearing any output, capturing history, advancing tick or invoking rules. Rejection preserves previous sidecar as well as events/rejections/state/capacities; callers consume output only on successful ticks. Accepted ticks replace previous sidecar even when all gates produce no outcomes. `clear` empties all channels while retaining the two allocations and inline storage.

No new GameEvent/NetworkEvent kinds, bytes, schemas, versions, checkpoint fields or context hashes. Sidecar is not serialized by network v5 or either existing replay adapter. Existing replay worlds keep their current event interface. Recomputed observations do not mutate global suppression state or suppress simulation.

pub struct PlayerTransitions {
    pub reload_started: bool,

    pub fn transition_count(&self) -> usize;

## Consumer and feedback ownership handoff

The executed `combat::PlayerStepResult` rustdoc recipe uses actual registered Match, Player snapshots, detailed local stepping, StepOutput and checkpoint restore. It starts a real reload, advances to completion, predicts completion+fire twice from the same snapshot, then executes/re-executes the same authority tick. Local observations remain speculative; a bounded caller confirmation ledger emits completion once. Another executed example on `step_player_with_settings_detailed` uses real short custom settings and checks accepted start/timer behavior.

Confirmed feedback belongs to the authority consumer and uses `(host_session, actor, full_life_generation, executed_tick)` for the aggregate record, or includes transition kind when flags are dispatched separately. Replaying/reconciling may legitimately reproduce the same observation. Keep a bounded ledger covering the supported reconciliation window, preserve it across ordinary reconciliation, and retire it at an explicit new session/discontinuous timeline boundary. Full u32 tick-cycle alias must also have a host session/generation boundary. Evicted records may be observed again; silent historical seek should not deliver live feedback. Optional speculative feedback requires its own explicit ownership/confirmation handoff. Pure local results contain no claimed authority/tick/session/life identity.
