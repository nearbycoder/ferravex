## Concrete behavior and lifecycle

- `EcsCommandBuffer::new(command_capacity, spawn_capacity)` reserves separate
  bounded pending-command, epoch-map and accepted-event buffers. Limits count
  operations/spawns, not payload bytes. There are no arbitrary queued closures.
  Payload tuples are sealed `Bundle + 'static`, zero through eight components,
  and need no Clone/Debug/Send/Sync bound. `unwrap` on a rejection separately
  requires Debug, as ordinary Result does; recipes use appropriate handling.
- Authoring never mutates the world. Spawns use task 213's actual checked
  `try_spawn_batch([bundle], &mut one_handle)` at apply. Hosts must explicitly
  prepare total sparse-index entity/component budgets; ordinary ECS growth does
  not grant those budgets. Insert/remove/despawn use checked ECS APIs. Insert
  retains legacy ordinary storage-growth behavior and is not a prepared insert.
- Tokens contain a private reference-counted buffer identity, checked u64 epoch
  and accepted-spawn slot. No raw/serializable constructor, identity bits,
  global ID counter or platform atomics were introduced. Tokens are Clone/Eq,
  not Copy; the adapter is thread-local/non-Send through Rc. Outstanding tokens
  retain identity after buffer destruction, so allocation-address reuse cannot
  make a fresh buffer accept an old token. No global identity storage grows.
- Only a successfully accepted spawn issues a token. Target operations accept
  existing Entity or earlier tokens. Authoring rejects foreign, stale, unissued
  and known-failed tokens; pending earlier tokens are valid dependencies. A
  private defensive apply check also rejects pending/unresolved/foreign/stale
  dependencies before executing their mutation. Forward token fabrication is
  unavailable publicly, with compile-fail and private adversarial coverage.
- Every spawn is consumed once. Pending becomes failed **before** invoking its
  executor, then becomes applied only after successful return. Reported failure
  or unwind can never bind the token to an unrelated or partially created entity.
  Dependent commands queued before failure subsequently fail explicitly.
- `apply_report` uses task 205's `CommandFailurePolicy`,
  `CommandFailure<EcsCommandError>` owned envelope and
  `FallibleCommandApplyOutcome`. Both errors and successes consume invocation
  budget. StopOnError reports one error and leaves the untouched FIFO tail;
  Continue reports all encountered errors within the same budget. Zero budget
  executes no command/callback. Errors/commands are never automatically retried.
- A minimal ECS executor is necessary instead of directly wrapping task 205's
  closure queue: it must borrow an external `&mut World` and separate token map,
  return a successful Entity/event, and return its original typed operation box
  on dependency/spawn rejection. Task 205 accepts only `FnOnce(&mut W) ->
  Result<(), E>`; using it directly would require owned World or shared
  interior-mutability context. This adapter reuses its actual public policy,
  error envelope and count outcome, without changing commands.rs or adding a
  second ECS. Domain ownership/success handling stays local to this module.
- Successful spawn mappings survive zero/partial/full applies and empty queues
  until explicit reset. `EcsApplyReport::take_spawn` and buffer `take_spawn` claim
  a mapping once; a repeat returns AlreadyTaken. Claiming does not remove the
  internal resolution used by queued or newly authored target commands. Map
  capacity covers **all accepted spawns in the epoch**, including failed and
  claimed ones; no slot is reused until reset. An empty queue does not end an
  epoch. Failure does not free its mapping slot.
- Mapping means accepted spawn, not current liveness. Later despawn can make a
  returned mapping stale, and subsequent operations on that token report checked
  NoSuchEntity even if another spawn reused the sparse slot. Existing Entity
  handles and mapped entities remain world-local: no foreign-world rejection is
  claimed. Apply every partial flush in an epoch to the same World. Reset before
  replacing the World; the adapter cannot prove World provenance.
- Each normally completed successful mutation records `{id, kind, entity}` in
  FIFO order. Reports borrow the bounded success log and epoch mapping; dropping
  a report loses no mapping. IDs are arbitrary caller correlation labels,
  including repeats/zero/max, and supply no event deduplication guarantee.
  `last_accepted` allows inspection after a later command/callback unwinds.
  Every apply, including zero budget, replaces the last log. Emit each accepted
  event once in the host; inspection does not consume/deduplicate feedback.
- Reset cancels all pending work, expires every old token, clears mappings/logs,
  and keeps accepted world entities and all allocated storage. It increments the
  epoch with checked arithmetic and never wraps. EpochExhausted returns before
  mutation: the current epoch can still flush, but a fresh buffer is needed for
  another epoch. Cancellation drops payloads without callbacks or mutations.
- Reset marks the buffer disabled and expires the epoch before dropping queued
  payloads one at a time. If a destructor unwinds, the untouched tail remains
  queued but apply/authoring/mapping claims return ResetIncomplete. A later
  successful reset finishes cancellation. This prevents an old existing-entity
  command from executing after interrupted reset. At the exhausted epoch a
  further reset can remain impossible; drop/recreate instead of reusing identity.

## Ownership, storage and panic policy

Authoring rejection returns `RejectedBundle<B> { reason, bundle }` before boxing
or consuming/dropping it; operation-capacity rejection takes precedence over
token/map validation. Spawn errors return the entire original bundle via the
owned failure. Dependency errors and stale insert targets also retain insert
bundles. `into_bundle::<B>()` recovers only the exact original tuple type; a
wrong type or absent payload returns the entire error unchanged. ECS insert's
own duplicate-component error consumes/drops its bundle according to the existing
checked API; no recovery is claimed for that case. Removed components are dropped,
not included in the output. Retrying recovered input is a new command/token and
explicit host decision, never an automatic replay of failed work.

Construction reserves VecDeque/Vec storage and one Rc identity using the ordinary
allocator. Accepted nonzero payload commands allocate one typed box; ZST
remove/despawn boxes need no heap allocation on this host. Successful/failed
apply paths move the existing box into errors, so they do not allocate another
payload box. Error delivery is synchronous to caller callbacks with no retained
error collection; successful reporting uses at most command_capacity entries.
Map storage uses at most spawn_capacity entries. Storage never grows beyond
these logical limits during adapter operation, and reset reuses allocations.
External token clones, arbitrary-size input payloads and host callback storage
are caller-owned, not a byte budget enforced by this adapter.

Every command is popped before invocation. No panic is caught or converted to a
domain error; no command, allocator, component construction/Clone/Drop, callback
or multi-command batch is promised transactional. Partial world mutations,
accepted earlier events and mapped earlier spawns remain; the unvisited tail is
preserved. A panicking spawn leaves Failed; remove/replacement/despawn Drop may
have mutated the world before unwinding and do not record successful completion.
A panic returns no report; `last_accepted`, queue length and one-shot mappings
remain inspectable. Hosts must assess world validity before resuming. No OOM,
allocator-abort or double-panic recovery guarantee is made.
