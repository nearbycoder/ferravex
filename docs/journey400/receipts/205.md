## Concrete behavior and compatibility

- Adds `FallibleCommandBuffer<W, E>` beside the unchanged `CommandBuffer<W>`.
  Existing struct fields, enum variants, signatures, normal-return accounting,
  lazy drain behavior and panic semantics remain intact. All 11 prior command
  tests remain in place.
- Accepts `FnOnce(&mut W) -> Result<(), E>` with a caller-supplied `u64` ID.
  IDs are correlation labels, **not generated handles**: zero, maximum and
  duplicate IDs are accepted verbatim, without deduplication or reordering.
  Consumers needing unique identity must assign unique IDs themselves. This
  accommodates the dependent ECS adapter's own token/request namespace without
  adding a second ID allocator or changing formats.
- Capacity is an immutable command-count limit. Storage grows lazily on accepted
  pushes and is retained after application/clear. A rejected push returns the
  original generic closure before boxing, invoking or dropping it. Retrying that
  never-executed closure appends it to the tail. Zero capacity rejects all pushes.
- `apply_report` takes an explicit `StopOnError` or `Continue` policy and an
  invocation budget. Both `Ok` and `Err` consume budget. Zero budget invokes
  neither commands nor the error callback. The stop policy reports its first
  error and retains every unexecuted command in FIFO order; continue reports all
  errors encountered within the same budget.
- Each domain error is synchronously moved, together with its ID, to `on_error`.
  The queue allocates no error collection and does not retain errors. The callback
  may write a fixed array, save the first error, or consume each error immediately.
  No `Clone`, `Debug`, `Error`, `Send` or `Sync` bounds are imposed on payloads.
  Only stored closures require `'static`; `W` and returned `E` need not be static.
- Reports distinguish started/successful/failed/remaining commands. Metrics also
  track accepted/rejected/discarded work and high-water mark; counters saturate.
  Resetting metrics preserves pending commands/IDs and starts the high-water mark
  at current queue length.
- Commands are removed before invocation. A command can mutate the world and
  then return `Err`; there is no rollback, transaction guarantee or automatic
  retry. A later explicit apply begins with the untouched tail.
- Command and callback panics propagate under both policies. `started` increments
  before invocation; `applied`/`failed` increment on normal return, with `failed`
  updated before the callback. Panics return no report, but metrics retain partial
  progress and the untouched tail stays queued. Hosts must assess world validity.
- `clear` discards stale work without invoking it or changing the world. It counts
  each command before dropping its payload; a destructor panic preserves the
  untouched tail. Normal queue destruction drops pending payloads without running
  their commands.
- No renderer, wall-clock, input, fixed-tick, wire/save/replay, export, feature,
  dependency or authored-game behavior changes. All production additions use std
  and safe Rust. The test allocator forwards to `std::alloc::System` with documented
  unsafe implementation, as in the existing J400204 instrumentation.
