## Concrete behavior and compatibility

The existing `HashMap<TypeId, Box<dyn Any>>` remains the only resource store.
Checked scoped callbacks provide two or three mutable references, one mutable
plus one shared reference, two mutable plus one shared reference, or one mutable
plus two shared references. Mutable arguments come first; callers reorder types
to select the resources to mutate. Entirely shared access continues to use the
existing `require`/`get` methods.

Validation uses real `TypeId` equality, fixed stack arrays of length two or three,
and safe `HashMap::get_disjoint_mut`, followed by safe `Any` downcasts. No engine
`unsafe`, cloning, remove/reinsert choreography, runtime borrow guards, resource
box replacement, or heap scratch allocation is introduced. The std lookup has
been stable since Rust 1.86, below the workspace's declared 1.88 requirement;
this run used Rust 1.96.1, not a separate 1.88 toolchain.

- Every requested type must be distinct, including shared/shared arguments.
  A Rust type alias is the same resource type. Distinct newtypes can hold separate
  roles with the same underlying representation.
- Duplicate validation precedes all missing-type checks, even for absent types.
  Indices are zero-based generic/callback argument positions. The earliest
  repeated position is `second`, with its earliest matching position as `first`.
- With no duplicates, the first missing argument in caller order produces
  `Missing { type_name, index }`. It remains a missing error at full capacity.
- Validation errors never invoke the callback and leave entries, contents and
  capacity unchanged. Success calls the callback exactly once with ordinary
  typed references and returns its result inside `Ok`.
- The resource count and 256-type cap are unchanged. Access works at capacity;
  successful and rejected lookups preserve existing allocation addresses.
- The outer `Result` only represents access validation. If a callback returns
  `Err(E)`, the result is `Ok(Err(E))`; `E` needs no trait or `'static` bounds.
  Mutations already performed by the callback, including shared interior
  mutations, persist on callback error or unwind. All resource entries remain
  installed after an unwind, and subsequent access works. There is no automatic
  retry or rollback. Task 016's checked replacement remains a separate operation.
- References cannot escape the callback, although results may borrow unrelated
  caller data. `FnOnce` captures and non-Clone/non-Send/non-Sync resources work.
- No existing public struct, enum, method signature, default, wire/save/replay
  format, native/Wasm export or feature gate changed. `ResourceError` remains
  exhaustively matchable with exactly `Missing` and `Capacity`.

## Exact public additions

All additions are in the existing `ferravex_engine::resources` module.
The following is a signature listing, not a standalone program:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ResourceAccessError {
    Duplicate {
        type_name: &'static str,
        first: usize,
        second: usize,
    },
    Missing {
        type_name: &'static str,
        index: usize,
    },
}

impl std::fmt::Display for ResourceAccessError;
impl std::error::Error for ResourceAccessError;

impl Resources {
    pub fn with2_mut<A: std::any::Any, B: std::any::Any, R>(
        &mut self,
        access: impl FnOnce(&mut A, &mut B) -> R,
    ) -> Result<R, ResourceAccessError>;

    pub fn with2_mut_ref<A: std::any::Any, B: std::any::Any, R>(
        &mut self,
        access: impl FnOnce(&mut A, &B) -> R,
    ) -> Result<R, ResourceAccessError>;

    pub fn with3_mut<A: std::any::Any, B: std::any::Any, C: std::any::Any, R>(
        &mut self,
        access: impl FnOnce(&mut A, &mut B, &mut C) -> R,
    ) -> Result<R, ResourceAccessError>;

    pub fn with3_mut_mut_ref<A: std::any::Any, B: std::any::Any, C: std::any::Any, R>(
        &mut self,
        access: impl FnOnce(&mut A, &mut B, &C) -> R,
    ) -> Result<R, ResourceAccessError>;

    pub fn with3_mut_ref_ref<A: std::any::Any, B: std::any::Any, C: std::any::Any, R>(
        &mut self,
        access: impl FnOnce(&mut A, &B, &C) -> R,
    ) -> Result<R, ResourceAccessError>;
}
```

`Display` includes diagnostic Rust type names and zero-based argument indices.
Both variants' `Error::source()` returns `None`. Names are diagnostic strings,
not stable serialization identifiers.

## Consumer recipe and parent registration

The runnable `Resources::with3_mut_mut_ref` rustdoc example composes the actual
first-party `work_budget::WorkBudget` and `events::EventQueue<u32>` with an
immutable job specification. It checks queue capacity before charging work,
enqueues only accepted jobs, and asserts successful admission, rejection when
the queue is full without charging again, draining, and rejection when the budget
is insufficient without emitting another event. It compiled and executed under
the scoped doctest command below. The other four methods and the error type
also have executable examples. A compile-fail doctest rejects returning a
resource reference from the callback.

Consumer handoff: an engine system or a loop like
`crates/ferravex-engine/examples/engine_pipeline.rs` can store its existing
budget, bounded event queue and job configuration in
`Resources`, then call `with3_mut_mut_ref` on an actual simulation tick. The
consumer retains budget-reset, event-drain, input, acceptance and clock ownership.
Inventory/objective consumers can instead use `with2_mut` with their existing
distinct resource types, validating domain operations themselves. No demo was
modified or required to adopt the helper.

Required source registrations: **none**. Verified existing
`crates/ferravex-engine/src/lib.rs` declares `pub mod resources;`, and
`crates/ferravex/src/lib.rs` has `pub use ferravex_engine::*;`. No root reexport,
manifest change, new module or feature flag is needed for these additions. The
engine public path was exercised by the doctests; no facade build is claimed.

Parent API-map adoption: in `docs/AGENT_GUIDE.md`'s **Task and API map**, add a
Journey400 203 resource-composition entry pointing to `resources.rs`,
`ResourceAccessError` and the five methods above; link the
`Resources::with3_mut_mut_ref` recipe. This documentation change and roadmap/task
