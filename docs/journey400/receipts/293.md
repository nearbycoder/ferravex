## Concrete behavior and compatibility

Actual `PadState` has 16 axes, 32 buttons, four slots and a connection epoch.
Profiles have fixed storage for 16 optional axis corrections and eight optional,
explicit, disjoint stick pairs. Construction checks complete input counts,
indices, duplicate corrections, overlapping/same-axis pairs, finite ranges and
finite deadzones before producing an immutable profile. Inspection borrows that
checked configuration; there is no serialized or automatically assigned identity.

Each selected signed axis maps `min -> -1`, `center -> 0`, `max -> 1` with separate
linear half-ranges. Require `-1 <= min < center < max <= 1`. Finite input extremes
clamp, and f64 intermediate math handles subnormal valid ranges without f32
overflow/underflow. Radial pairs run afterward: radius <= deadzone becomes zero,
the remaining radius remaps linearly to fullscale at radius 1, and diagonals
outside the unit disk retain direction at fullscale. Require `0 <= deadzone < 1`.
Rounding to f32 is ordinary floating-point rounding, not a determinism guarantee.

`CalibrationProfile::default()` has no corrections/pairs. In-range finite samples
preserve axis bits; finite out-of-range axes clamp exactly as the existing host
boundary does. Every button is copied bit-for-bit by pure calibration, then the
existing host boundary retains its original button clamping. Calibration never
derives button/trigger/hat values from its adjusted axes. Linux ioctl mapping,
raw normalization, button/trigger/hat defaults, native polling, PlayerInput
settings, exported browser ABI and wire/save/replay formats remain unchanged.

The new opt-in helper rejects any nonfinite connected axis OR button before any
axis/button feed. On error the journal, selected profile and last-good raw sample
remain unchanged, including when the rejected sample claims a new epoch. This is
deliberately stricter than direct legacy `gamepad_sample`'s per-value nonfinite
fallback; the legacy function itself is unchanged. Disconnected samples ignore
stale invalid values and become neutral, so disconnect cannot be blocked by NaN.

`CalibratedGamepad` owns an explicitly chosen slot, one connection-local profile
and one last-good raw sample. Creation does not write host state. Selection fails
while disconnected; there is no profile waiting silently for the next device.
Selecting/replacing/resetting immediately resubmits all axes from the retained
raw sample, undoing prior corrections without stale axis values. Unchanged
buttons add no journal events and pending tick edges are not consumed. Reset
clears selection, preserves connection and restores ordinary raw drift/defaults;
it is not a synthetic button release. Disconnect clears selection and raw state,
neutralizes the slot, and is idempotent.

Disconnect/reconnect or a changed host-supplied raw epoch clears selection.
A valid changed epoch also submits disconnect/reconnect through the actual host
boundary, preserving PlayerInput's existing hotplug held suppression. The supplied
epoch is only the host's connection generation; it does not replace the platform
journal's independently generated epoch. With no stable hardware IDs available,
replacement without observed disconnect requires an explicit `disconnect()` or
changed supplied epoch. Use one producer per slot on one host thread. There is no
global exclusive-slot registry, thread-migration enforcement or drop-time I/O.

## Exact public API

All new items are under `ferravex_render::input::calibration`.
The following is a signature inventory, not a standalone compiling example.

```text
pub const GAMEPAD_SLOTS: usize = 4;
pub const CALIBRATION_AXES: usize = 16;
pub const CALIBRATION_STICKS: usize = CALIBRATION_AXES / 2;

pub struct AxisCalibration { pub min: f32, pub center: f32, pub max: f32 }
pub struct RadialStick { pub axes: [usize; 2], pub deadzone: f32 }

#[non_exhaustive]
pub enum CalibrationError {
    InvalidSlot { slot: usize }, TooManyAxes, TooManySticks,
    InvalidAxis { axis: usize }, DuplicateAxis { axis: usize },
    InvalidRange { axis: usize }, InvalidDeadzone { stick: usize },
    OverlappingStick { axis: usize }, NonFiniteAxis { axis: usize },
    NonFiniteButton { button: usize }, Disconnected,
}

pub struct CalibrationProfile { /* private checked fixed storage */ }
impl CalibrationProfile {
    pub fn try_new(axes: &[(usize, AxisCalibration)], sticks: &[RadialStick])
        -> Result<Self, CalibrationError>;
    pub fn axes(&self) -> &[Option<AxisCalibration>; CALIBRATION_AXES];
    pub fn sticks(&self) -> &[Option<RadialStick>; CALIBRATION_STICKS];
    pub fn apply(&self, raw: PadState) -> Result<PadState, CalibrationError>;
}

pub struct CalibratedGamepad { /* private slot, selection, last raw */ }
impl CalibratedGamepad {
    pub fn new(slot: usize) -> Result<Self, CalibrationError>;
    pub fn slot(&self) -> usize;
    pub fn profile(&self) -> Option<&CalibrationProfile>;
    pub fn last_raw(&self) -> &PadState;
    pub fn submit(&mut self, raw: PadState) -> Result<(), CalibrationError>;
    pub fn select_profile(&mut self, profile: CalibrationProfile)
        -> Result<(), CalibrationError>;
    pub fn reset(&mut self);
    pub fn disconnect(&mut self);
}
```

AxisCalibration/RadialStick derive Clone, Copy, Debug, PartialEq.
CalibrationProfile additionally derives Default. CalibrationError derives Clone,
Copy, Debug, PartialEq, Eq and implements Display/std::error::Error.
CalibratedGamepad implements Debug and is not Clone/Copy.

## Consumer handoff and runnable evidence

The module-level `rust,check` doctest is a compiled **and executed** headless
first-party recipe: construct an actual PadState, submit raw samples through the
adapter and real `gamepad_sample` journal, then use `host_frame`/transient
PlayerInput and actual `GameSession::advance` ticks. Real mappings are left stick
PadAxis(0/1), jump PadButton(0); integration tests also exercise trigger
PadButton(7), right-hat PadButton(15), and Linux mapping fixtures remain passing.
The recipe preserves a press/release tap through a zero-tick frame and consumes
it exactly once across two scheduled/executed input updates. It never writes
game state/memory/time to fabricate hardware or gameplay results.

Adoption: a custom Rust embedding host using `host_frame` should create one
adapter for its slot, submit a connection baseline, explicitly select the checked
profile, and route subsequent **raw normalized** samples through `submit` once.
Do not also feed that slot with native polling/direct gamepad_sample, and do not
pass pre-calibrated output back into the adapter. `apply` is separately available
for tools/pure composition. PlayerInput retains its independent response settings:
the recipe sets pad_deadzone=0 and pad_curve=1 to avoid a second deadzone/remap.
That change is explicit in the consumer, not a global/default settings change.
