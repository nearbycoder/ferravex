## Concrete behavior and compatibility

- Call the existing finish method, then inspect the result before translating
  this frame's fresh pointer edges into scene requests. Reads only copy a small
  fixed-size value: no allocations, gameplay-action consumption, journal drain,
  new ActionMap context or second input framework.
- `pointer_consumed` aggregates any UI-owned primary-pointer gesture that starts,
  remains held, releases or cancels in that host frame. A successful pointer
  activation is always consumed. It stays consumed through drag-out, release
  outside, removal/disablement of the original widget, explicit cancel/Escape,
  closing a modal and disabling UI. `pointer_capture` names the original owner
  until its terminal event, including an inert cancelled tail and a removed ID.
  Cancelled tails cannot be stolen by a second mouse/touch start.
- `pointer_activated` is the last accepted pointer release. Enabled topmost
  buttons capture and activate using the existing `UiState` behavior. Disabled
  topmost buttons own the gesture and block the world/lower buttons, without
  activation or keyboard focus. Fully clipped widgets do not own a press;
  partially clipped widgets use the same rect/clip and logical viewport mapping
  as the existing hit test. Half-open bounds remain unchanged.
- Panels/text remain paint-only, even if opaque. Use `Ui::modal` to explicitly
  block the logical viewport. Modal layout discards lower interaction widgets
  but keeps their paint commands. Its nonfocusable blocker ID can appear as a
  pointer activation, matching existing `UiState` behavior. Modal tracking uses
  an index into the existing command arena and one blocker ID, not another list.
- Ownership is assigned on press. A world-origin gesture dragged onto UI stays
  world-owned. It cannot activate a button merely by releasing there. Hover
  alone does not set `pointer_consumed`.
- `keyboard_confirmed` reports an accepted built-in Enter activation;
  `gamepad_confirmed` reports accepted selected-pad A; `player_confirmed` reports
  accepted remapped global `confirm`. These report acceptance, not merely a
  physical key press. The remapped route's physical device is deliberately not
  guessed. A binding may overlap a built-in route. Auto-focus, explicit-focus
  behavior and fresh-gamepad suppression retain their defaults.
- Existing `finish_player` consumption of the **global** `confirm` is preserved,
  including when no widget accepts it. It does not consume unrelated movement,
  jump, fire or other gameplay actions. The tests preserve held keyboard
  movement and a pending jump tap across multiple zero-tick frames and catch-up
  ticks. The new result does not retroactively remove a UI click from an
  independently bound gameplay action: consumers must follow the order below.
- Focus loss, journal overflow and the host Controls editor set `input_blocked`.
  Once observed, it stays true for that host frame even if the editor closes
  before another finish. Callers should cancel their own scene gestures too,
  while authoritative network/replay ticks continue. Focus-epoch changes or
  overflow reset ownership because the journal cannot establish a valid tail;
  no stale release activates UI. A normal `finish(false)` disables UI without
  itself blocking the world, but still accounts for a previously owned tail.
- New-frame finish resets transient summary fields and preserves a held owner.
  Repeated reads/finishes, including another `begin` in the same host frame,
  retain the aggregate and never replay the frame journal. Inspect after finish:
  `begin` alone does not manufacture a new host-frame result. Rebuilding layout
  and finishing once after the host pumps events remains the normal contract.
- The result is intentionally conservative and bounded, not an event queue.
  Multiple gestures share one consumed flag; multiple activations retain the
  last accepted ID per source. Existing `activated` still reports the last ID
  overall. A UI gesture and a valid world click in the same frame can therefore
  suppress the latter. Only this `Ui` instance's existing primary-mouse/one-touch
  route is classified. Secondary mouse buttons, additional touches, legacy free
  button helpers and separately routed scroll/UI systems need caller policy.
- Existing command/widget/text/vertex/clip bounds remain 1024/1024/32 KiB/
  196608/16. No new dynamic storage. Rejected capacity, duplicate-ID and invalid
  style submissions never become interaction owners. `reserved_bytes` includes
  the added fixed fields through its existing `size_of::<Self>()` calculation.

## Consumer handoff / runnable recipe

The executed `Ui::interaction` rustdoc is a complete first-party headless recipe.
It injects ordinary primary-touch journal events in logical pixels, samples
`PlayerInput`, submits/finishes/paints a Buy button, classifies the fresh pointer
press, and keeps accepted Buy/Drop requests in a bounded one-slot caller queue.
The first Buy occurs on a zero-tick frame. Two later drops are rejected while
the queue is full; the first actual tick executes Buy. A subsequent world Drop
executes once. A jump action is consumed only inside executed ticks. Assertions
check the exact `[Buy, Drop([180., 160.])]` execution sequence. Queue-full policy
is explicit rejection without overwriting; the observation Vec is test output,
not the command queue. The recipe documents clearing pending commands on restart
and emitting feedback only after rules accept a command.

Orchard parent (`examples/orchard-guard/src/game.rs` and its presentation/input
composition): collect each frame's fresh plot pointer press/position; sample the
player; submit and finish the Buy/menu UI; read `ui.interaction()`. Translate a
plot-selection request only when both `pointer_consumed` and `input_blocked` are
false. Queue accepted UI/scene requests until an actual update, apply the game
rules there, then emit accepted-event feedback. A UI release may close the menu;
keep calling the same `Ui` finish on following frames, even with an empty layout
or `enabled = false`, so the owned release/cancel tail is observed.

Physics 2D parent (`examples/physics-2d/src/lib.rs` and its presentation adapter):
use the same order before translating a fresh pointer into a drop request or
starting a drag. Begin scene drags only from unconsumed world-origin presses;
retain that scene owner through move/release. Cancel scene gestures on
`input_blocked`. Queue accepted drop/drag commands for actual ticks, including
zero-tick render frames. Do not apply a later frame's summary to a pending
`PlayerInput::take_tick(["fire"])` edge from an earlier UI frame. Keep unrelated
keyboard/gamepad movement on the existing tick-snapshot path.

No additional play-level seam is required for that recipe. Native embedding,
demo adoption and any facade imports remain parent-owned. Future task 281
rollback/checkpoint work must account for `modal_start`/`modal_blocker` together
with widget/command state; this task does not introduce a composition transaction.
