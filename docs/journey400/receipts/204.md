## Concrete behavior and compatibility

- The schedule owns **one existing `SystemOrder`**, with callback/predicate
  metadata and a cached vector of entry indices. No second dependency graph or
  executor is introduced. `prepare` uses `resolve_checked`, which delegates to
  `SystemOrder::resolve`; it never flattens layers. Newly ready entries retain
  the existing earliest-registration tie-break. Read-only `order()` exposes the
  original inspection APIs without permitting untracked mutations.
- The graph enforces the unchanged 256-name capacity and 1–128 UTF-8 byte names.
  Systems, flush boundaries and unbound names share that cap. Capture/payload
  bytes and callback execution time remain caller controlled, not bounded by the
  entry limit. Production code remains safe Rust/std-only.
- Construction is empty and unprepared, with no callback execution. `register`
  and `register_flush` create enabled, unconditional entries. `add` declares a
  name to bind later with `set_callback`. Preparation rejects the first missing
  callable in resolved sequential order, **even when disabled**. A graph cycle
  takes precedence; it uses the existing named `OrderDiagnostic`. Failure exposes
  no runnable partial sequence and invokes neither callbacks nor predicates.
- Every successful configuration edit invalidates preparation, including an
  idempotent edge/enablement/predicate edit. Rejected edits preserve the previously
  prepared configuration. `before` retains the existing deferred cycle checking;
  `before_checked` retains its transactional rejection. Repeated `prepare` on an
  unchanged prepared schedule is a no-op. Binding/replacing a callable retains
  the entry's system/flush kind, predicate and enablement.
- `set_run_if` opts into a stateful `FnMut(&C) -> bool`. It sees current context
  immediately before that entry, including earlier mutations and flushes. Explicit
  disablement bypasses both predicate and callable. A false predicate skips only
  that entry. Dependencies constrain order, not successful execution, so disabled
  prerequisites do not disable dependents. These rules also apply to flushes.
- Flush boundaries are explicit named callbacks using the same ordering graph,
  capacity and stop/error rules. The host declares edges on both sides and owns
  which queue to apply and its application budget. There is **no implicit initial,
  final, stop, error or clear flush**. The runnable recipe and tests use the actual
  existing `CommandBuffer::push`/`apply`; task 205's proposed API is not required.
- `run` refuses an unprepared schedule before invoking anything, then dispatches
  cached indices without name searches, graph resolution or runner allocations.
  Stop or callback error immediately suppresses later predicates, systems and
  flushes. Error returns the original `E`, borrowed name, kind and prefix report,
  with no `Clone`, `Debug`, `Send` or error-trait bound needed for execution.
- Reports count all scheduled entries, invoked callbacks (including failing or
  stopping ones), visited skips, invoked flushes (a subset of callbacks) and
  Continue/Stop. `scheduled - invoked - skipped` is the suppressed tail. A report
  counts callbacks, not ticks, commands applied, successful commits or frames.
  Callback error reports have Stop control.
- Stop is local to the invocation, not a permanent lifecycle latch. Any later
  explicit run starts at the beginning, retaining callback/predicate capture
  state. Nothing retries automatically. Mutations and pending commands are not
  rolled back. Callback/predicate panics propagate, suppress the tail, and return
  no report; the host decides whether the context is valid for reuse.
- `clear` installs a new empty, unprepared configuration before dropping old
  captures; even a captured destructor panic leaves the new empty configuration
  installed. It releases configuration storage without invoking callbacks and
  leaves caller-owned context/queues/session state untouched. Captures dropped by
  rejection/replacement/clear are ordinary Rust values; their destructors may run
  arbitrary host code. Registration rejection drops its supplied closure.
- Callback/predicate captures are owned (`'static`) and need not be `Send`.
  `C` itself can contain borrowed data, exercised by a regression. No timing,
  input consumption, rendering, wall clock or platform work is owned by the runner.

## Exact public APIs

All types below are in `ferravex_engine::systems`. These are signature excerpts;
the six actual source examples were compiled and executed as recorded below.

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum SystemControl { Continue, Stop }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum SystemEntryKind { System, Flush }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
#[must_use]
pub struct ScheduleReport {
    pub scheduled: usize,
    pub invoked: usize,
    pub skipped: usize,
    pub flushes: usize,
    pub control: SystemControl,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum SchedulePrepareError {
    Order(OrderDiagnostic),
    MissingCallable { name: String },
}

#[derive(Debug, PartialEq, Eq)]
pub enum ScheduleRunError<'a, E> {
    NotPrepared,
    Callback {
        name: &'a str,
        kind: SystemEntryKind,
        error: E,
        report: ScheduleReport,
    },
}

pub struct SystemSchedule<C, E> { /* private */ }
impl<C, E> Default for SystemSchedule<C, E>;

impl<C, E> SystemSchedule<C, E> {
    pub fn add(&mut self, name: &str) -> Result<(), OrderError>;
    pub fn register<F>(&mut self, name: &str, callback: F) -> Result<(), OrderError>
    where F: FnMut(&mut C) -> Result<SystemControl, E> + 'static;
    pub fn register_flush<F>(&mut self, name: &str, callback: F) -> Result<(), OrderError>
    where F: FnMut(&mut C) -> Result<SystemControl, E> + 'static;
    pub fn set_callback<F>(&mut self, name: &str, callback: F) -> Result<(), OrderError>
    where F: FnMut(&mut C) -> Result<SystemControl, E> + 'static;
    pub fn set_run_if<F>(&mut self, name: &str, predicate: F) -> Result<(), OrderError>
    where F: FnMut(&C) -> bool + 'static;
    pub fn clear_run_if(&mut self, name: &str) -> Result<(), OrderError>;
    pub fn set_enabled(&mut self, name: &str, enabled: bool) -> Result<(), OrderError>;
    pub fn before(&mut self, first: &str, second: &str) -> Result<(), OrderError>;
    pub fn before_checked(&mut self, first: &str, second: &str) -> Result<(), OrderDiagnostic>;
    pub fn order(&self) -> &SystemOrder;
    pub fn len(&self) -> usize;
    pub fn is_empty(&self) -> bool;
    pub fn is_prepared(&self) -> bool;
    pub fn prepared_names(&self) -> Option<impl ExactSizeIterator<Item = &str> + '_>;
    pub fn prepare(&mut self) -> Result<(), SchedulePrepareError>;
    pub fn run(&mut self, context: &mut C) -> Result<ScheduleReport, ScheduleRunError<'_, E>>;
    pub fn clear(&mut self);
}
```

`SchedulePrepareError` implements `Display` and `std::error::Error`, with its
underlying ordering diagnostic as the source. `ScheduleRunError<'_, E>` implements
`Display` when `E: Display`, and `std::error::Error` when
`E: std::error::Error + 'static`, exposing the original callback error as source.
`OrderError` and `OrderDiagnostic` are reused from the existing `system_order`
module unchanged. Existing public struct literals, exhaustive enums and defaults
elsewhere are unaffected.

## Registration and consumer handoff

**Required engine registration is already applied under the coordination grant:**
`pub mod systems;` in `crates/ferravex-engine/src/lib.rs`, after `system_order`.
No other module/root/manifest registration is required. Source inspection shows
the existing `pub use ferravex_engine::*;` in `crates/ferravex/src/lib.rs` should
also expose `ferravex::systems`; that facade path was not built by this task.
Parent owns facade documentation/prelude choices and any downstream adoption.

The module-level executable recipe is the first-party consumer handoff: register
motion, a named CommandBuffer flush and a consumer in intentionally different
registration order; constrain the flush on both sides; prepare; feed each actual
`GameSession::advance_batch(...).ticks()` context to one run. A zero-tick frame
runs no systems. Its assertions verify the published position and tick ID.

The inline App integration regression supplies a concrete `Game` adapter:
`fixed_update_context` stores task 201's `TickContext` in the simulation context,
calls the schedule once, maps `SystemControl` to `AppControl`, and extracts the
owned callback `E` from `ScheduleRunError` for `Game::Error`. The borrowed diagnostic
name need not be retained by the game. This checks actual App dispatch: zero work
does not run a system; four scheduled ticks with Continue execute four callbacks;
Stop/Err on the first executes one while the session retains all four issued IDs.

Consumers should prepare after configuration, keep input-edge consumption inside
actual update callbacks, and retain authoritative-phase guards for custom tick
batches. Schedule counts are per-entry, so use the existing App report (or a host
tick counter) for executed ticks. Restart must reset caller-owned commands/input/
simulation separately; clear/rebuild the schedule only if its configuration or
captured state also needs replacing. Local menu predicates must not disable
authoritative network/replay progression. Accepted game events still own feedback.
