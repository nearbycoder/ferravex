## Concrete semantics

- The callback receives `&EventPacket`, including borrowed `payload` storage.
  The production path allocates nothing and clones neither packet nor payload.
  Callback work may allocate; initial queueing still copies payloads as before.
- Only a callback returning `true` changes that packet's `last_sent` to `now`.
  Returning `false` refuses that packet and stops immediately. Prior acceptances
  persist. The refused packet and untouched tail retain their timestamps.
- Visits alone do not imply acceptance. A locally accepted send remains pending
  until its own individual `acknowledge(sequence)` succeeds.
- Offered packets follow increasing sequence among currently due packets.
  Previously sent packets still awaiting their retry are skipped, just as in
  legacy `due`. The first due packet exceeding the remaining byte budget stops
  the batch; smaller later packets are not packed ahead of that head.
- `packet_budget` limits callbacks and accepted packets; refusal is the final
  callback. Window storage independently caps scanning/callbacks at 256 packets.
  The delivery pass plus the report pass each scan at most the bounded window.
- `byte_budget` is **payload bytes only**. Sequence numbers, lengths, protocol
  header/session fields, UDP/IP and other encoding overhead are excluded.
  `payload_bytes` sums only accepted payloads. Empty payloads consume a packet
  budget unit but zero bytes, so they fit a zero-byte budget. A preceding
  nonempty due packet still blocks a later empty packet under too-small budget.
- `remaining_due` exactly counts pending packets still eligible at this same
  supplied `now` after successful return. It includes refused/over-budget heads
  and all untouched due tail packets; it excludes accepted retry-waiting packets.
  Zero packet budget is a nonmutating way to count current due work.
- Caller supplies monotonic milliseconds, from a consistent domain when mixing
  `send_due` and legacy `due`. There is no I/O or clock read/validation. All batch
  acceptances share one sampled time. The retry interval remains 100 ms using
  saturating subtraction. Backwards time delays previously sent retries as in
  the legacy API; the implementation does not add a new clock-error variant.
  At `u64::MAX`, a send cannot become due again without replacing the sender.
- The exclusive sender borrow prevents safe same-sender callback reentrancy,
  including queue/ACK mutation. Encode synchronously, or explicitly copy for an
  owned outbound queue. Perform receiver ACK application after the batch.
- With panic unwinding, previous accepted timestamps persist; the panicking
  packet and tail retain original timestamps, including an old retry timestamp.
  No report returns on panic. Callback side effects are not rolled back; sending
  externally and then returning false/panicking can produce retries/duplicates.
  Aborting panics end the process rather than providing recovery guarantees.

## Compatibility and bounded failures

`EventPacket` fields, `Error::{Full,Oversized,SequenceExhausted,OutsideWindow}`,
`EventSender` defaults, `queue`, `due`, individual ACKs and all receiver methods
retain their existing contracts. Legacy `due(now, budget) -> Vec<EventPacket>`
still marks and clones each selected packet, with its existing packet-only
budget. Its eligibility predicate was factored into private `Pending::is_due`
so both paths use the same retry rule.

The 900-byte payload and 256-packet pending limits are unchanged, including
Oversized-before-Full queue error precedence. Sending does not free window
capacity. Unknown/duplicate ACKs do not remove another packet. Sequence
exhaustion retains the old no-wrap behavior: `u64::MAX - 1` is the final queueable
sequence; trying to queue when next is `u64::MAX` returns SequenceExhausted and
leaves pending work intact. No new reset API was invented: existing replacement
with `EventSender::default()` drops pending work and resets sequence/timestamps;
use a new transport session so delayed old ACKs cannot acknowledge new work.
No wire/save/replay version or encoded byte layout changed.

## Consumer and root-registration handoff

No root/module/manifest registration is required: existing
`crates/ferravex-net/src/lib.rs` already declares `pub mod reliable;`. The new
method/report are immediately callable through that registered module, as
proved by external integration tests and doctests. No requested facade edit was
made; parent owns any optional facade/prelude reexport and native/Wasm checks.
Task 312 can later extend the receiver in this file without replacing send code.

The complete runnable `EventSender::send_due` rustdoc recipe drives the actual
existing `EventReceiver`: accept and lose first packet at time 0, refuse second,
send second at time 1, ACK it individually while first remains pending, verify
no first retry at 99, recover ordered delivery at 100 and ACK first. The task
integration test additionally exercises three packets and duplicate receive.
These are pure supplied-time recipes, not a new transport or protocol.

Inspected existing consumers before designing the addition:

- `crates/ferravex-fps/src/network.rs::GameServer::flush_events` currently calls
  `peer.events.due(now, EVENT_SEND_BUDGET)`, constructs an owned ReliableEvent,
  encodes and sends. Parent authority adoption should use `peer.events.send_due`
  and return true only after actual outbound admission/full datagram acceptance.
- `crates/ferravex-fps/src/network/tactical.rs::GameClient::flush_commands`
  currently calls `self.commands.due(..., 8)` before encoding/sending the owned
  tactical command. Parent client adoption follows the same acceptance rule.
- Existing `network.rs::send_ok` maps WouldBlock to `Ok(())`. Do **not** use
  `send_ok(...).is_ok()` as this callback's acceptance: WouldBlock must refuse,
  leaving the packet immediately eligible. Retain fatal errors outside the bool
  callback and propagate them after `send_due` returns. For datagrams require
  the complete encoded length to be accepted; short/failed sends return false.
- Existing `encode_server(&ServerPacket)` / `encode_client(&ClientPacket)` accept
  owned packet enums and return allocating Vecs. This send-only task does not
  pretend those codecs now support borrowed envelopes: cloning explicitly to
  construct one remains a compatible transitional option, while a parent-owned
  borrowed encoder adapter is needed to preserve zero cloning throughout FPS.
  No new codec/protocol is implemented here. Existing v5 ReliableEvent and
  tactical Command envelopes each add 24 bytes before payload (6 header +
  8 session + 8 sequence + 2 length); a payload budget is not a wire budget.
  Apply any whole-wire/transport capacity in the callback before acceptance.
- For actual receiver consumers, ACK only on successful `receive`, including
  duplicates, as before. An outbound callback returning true is local acceptance,
  never authorization to manufacture a receiver ACK.
