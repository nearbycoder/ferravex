## Concrete behavior and compatibility

- `try_teleport` operates on a live body reference; `try_teleport_body` additionally
  validates its generational world handle before looking at pose fields. A stale
  handle cannot mutate a replacement in its old slot. Handles retain the existing
  same-world requirement; they do not contain a world identity.
- Validate finite body-origin translation, normalize/check the rotation, then
  check contact-revision capacity **before any mutation**. Invalid translation,
  zero/non-finite rotation and revision exhaustion preserve every core field,
  accumulated force/torque, pending targets, sleep state and world snapshots.
  The dimensional 2D rotation constructor already rejects non-finite angles;
  the core additionally rejects rotations that do not preserve the plane.
- All finite nonzero 3D quaternion scales are accepted using existing math
  checked normalization, including representable subnormal and huge values.
  Returns the actual committed normalized quaternion or wrapped planar rotation,
  alongside the committed body-origin translation, for host interpolation snap.
- Callers must explicitly select `VelocityPolicy::Preserve` or `Clear`.
  `TeleportOptions::new(policy)` clears force/torque and both pending kinematic
  targets. Either clear flag can independently be set false. There is no implicit
  `Default` velocity/reset policy.
- `Clear` zeroes stored linear and angular velocity. `Preserve` retains stored
  world-space COM linear velocity and angular velocity; it does not preserve
  body-origin point velocity or angular momentum when orientation changes.
  No mass/inertia, child transform, gravity scale, damping or CCD setting changes.
- Retained force/torque applies during the next ordinary dynamic step and is
  then consumed normally. A kinematic body's next step derives velocity from
  retained targets, or zero without targets, as before. Retained position and
  rotation targets are still executed and can move the body away from the
  committed pose on that step; clearing targets prevents the old snap back.
  Fixed bodies retain their existing immobility during integration.
- Every success, including an identical-pose reset, advances the existing body
  revision exactly once, marks solver state dirty, wakes the edited body
  immediately and resets its quiet timer. Existing production passes wake old
  solid contact islands before integration, new solid contacts before solving,
  and enabled joint islands on the next valid step. Sensors do not join wake
  islands; unrelated sleepers stay asleep. No timestep is issued or executed.
- Revision mismatch cold-starts affected contact features and clears attached
  joint warm-start rows in the existing pre-solve refresh. Unaffected contact
  feature identities survive. Last-step contacts, manifolds, events and stats
  remain snapshots until the next valid step, matching existing pose setters;
  their old impulses cannot be reused after the revision change. Stop events
  are emitted once by the normal next-step lifecycle, without synthetic events.
- Body, collider and joint handles, child order, mass/COM, joint local anchors,
  descriptions, limits, filters and motor settings remain intact. Existing joints
  may correct the teleported pose or break at a later step under their ordinary
  constraints/break policy. Teleport itself creates/removes no identity.
- No new collection, scratch storage, scan or allocation is required by these
  methods. Calls work at the 4096-body and 32-child capacities. Existing setters,
  builder signatures, struct literals, exhaustive enums, save/replay/wire formats
  and simulation defaults are unchanged. No engine/game dependency was added.

This is pose/reset authoring, not collision-safe destination search. Task220
queries can inform application placement policy before calling this operation;
one overlap witness is not a safe world-placement solution.

## Exact public API

Signature reference (not a standalone runnable snippet). In both
`ferravex_physics::d2` and `ferravex_physics::d3`, with their existing `Vector`
and `Rotation` aliases:

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct RigidBodyPose {
    pub translation: Vector,
    pub rotation: Rotation,
}
impl RigidBody {
    pub fn try_teleport(
        &mut self,
        pose: RigidBodyPose,
        options: TeleportOptions,
    ) -> Result<RigidBodyPose, TeleportError>;
}
impl PhysicsWorld {
    pub fn try_teleport_body(
        &mut self,
        body: RigidBodyHandle,
        pose: RigidBodyPose,
        options: TeleportOptions,
    ) -> Result<RigidBodyPose, TeleportError>;
}
```

Shared policy/error types are defined in `body.rs` and publicly reexported from
**both** dimensional modules by owned `api.rs`. The two paths name the same
shared policy/error types; `RigidBodyPose` remains dimension-specific.

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum VelocityPolicy { Preserve, Clear }

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
#[must_use]
pub struct TeleportOptions {
    pub velocity: VelocityPolicy,
    pub clear_forces: bool,
    pub clear_kinematic_targets: bool,
}
impl TeleportOptions {
    pub const fn new(velocity: VelocityPolicy) -> Self;
}

#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum TeleportError {
    InvalidHandle,
    Translation,
    Rotation,
    RevisionExhausted,
}
// TeleportError implements std::fmt::Display and std::error::Error.
```
