## Behavior and compatibility

- `new(capacity)` keeps its signature and behavior and has zero scope capacity.
  It still allocates no initial queue/scope storage. Existing schedule, cancel,
  reschedule, ready iterator, collecting drain and bounded output-buffer methods
  keep their signatures and payload-only outputs.
- Opt-in construction preallocates exactly the configured scope-slot count and
  one shared identity allocation for nonzero scope capacity. Task capacity and
  live-scope capacity are independent; a zero-task-capacity scheduler can still
  create/cancel scopes. Task storage remains the existing bounded BTreeMap;
  scoped and unscoped jobs share one task limit and task-ID sequence.
- Scope handles have private scheduler identity, slot and generation. Clones
  identify the same scope; handles are Clone, not Copy. Identity uses Arc pointer
  equality rather than the unit payload's value equality. It survives moving
  the scheduler and stays alive in stale handles, preventing foreign scheduler
  aliasing, including after the original scheduler has been dropped.
- Creation increments a free slot's generation. A slot reaching `u64::MAX` is
  usable for that final generation, then permanently retires on cancellation;
  it never wraps and revives a stale handle. No task IDs are consumed by scope
  creation/cancellation/rejection. Generational exhaustion is tested with private
  state injection, rather than attempting billions of lifecycle iterations.
- A full scope pool returns `None` without mutation. Empty/drained scopes retain
  their slots until explicit scope cancellation; dropping the last handle does
  not cancel work or release its slot. Dropping all handles can therefore strand
  that slot for the scheduler's lifetime. Hosts should retain lifecycle handles.
- Scoped scheduling returns the original payload unchanged on a foreign/stale
  scope, full task queue or exhausted task-ID sequence. Rejection neither drops
  the payload nor consumes capacity/IDs. Error reasons are deliberately reported
  through the same payload-returning Result shape as existing scheduling.
- Membership stays with a task across rescheduling. Deadline keys remain
  `(absolute_tick, original_task_id)`: all equal-deadline ties, including mixed
  scoped/unscoped jobs and jobs moved earlier/later, preserve original FIFO.
  Cancellation never resets another task's deadline, membership or ID.
- Scope cancellation first invalidates the scope and then visits only its queued
  jobs in deadline/FIFO order. `cancel_scope` discards payloads; callable payloads
  are not executed. `cancel_scope_with` transfers `(TaskId, payload)` ownership
  to a callback for reclamation/retention/disposal. It returns `Some(count)` for
  a live scope, including `Some(0)` when empty; foreign/stale scope handles return
  `None` and never invoke the callback. Already drained/cancelled jobs are outside
  scope cancellation, including payloads retained by the caller.
- On callback/destructor panic with unwinding, the current job is already removed;
  a private guard discards every unvisited member without invoking additional
  callbacks. The scope remains invalid, other jobs remain queued, and caller-
  retained payloads remain caller-owned. The scheduler is exclusively borrowed
  throughout cancellation; a compile-fail rustdoc verifies callback reentry is
  rejected. Double destructor panic and panic=abort follow ordinary Rust policy.
- Scope acquisition, validation, cloning and cancellation allocate no new
  storage after construction. Cancellation scans queued jobs plus tree lookup/
  removal costs, without a temporary collection. Tree removals may deallocate.
  Scheduling/rescheduling may still allocate BTreeMap nodes, as before. Callback
  code and payload destructors can allocate or have arbitrary side effects.
- No simulation timer, clock, platform I/O or renderer was added. Deadlines retain
  ordinary numeric u64 ordering, not modular ordering. Hosts must cancel old
  timeline scopes before clock restart/reset/wrap, dispose of retained batches
  and separately handle any unscoped jobs on that timeline. Task IDs never reset
  within a scheduler; legacy TaskId remains scheduler-local without runtime
  foreign-ID checking. New ScopeId has explicit runtime provenance checking.

## Exact added public API

All paths below are in `ferravex_engine::scheduler`; signatures are reference
excerpts, not standalone snippets.

```rust
#[derive(Clone, Debug)]
pub struct ScopeId { /* private fields */ }
impl PartialEq for ScopeId { /* identity + slot + generation */ }
impl Eq for ScopeId {}

impl<T> TickScheduler<T> {
    pub fn with_scope_capacity(capacity: usize, scope_capacity: usize) -> Self;
    pub fn create_scope(&mut self) -> Option<ScopeId>;
    pub fn is_scope_active(&self, scope: &ScopeId) -> bool;
    pub fn schedule_scoped(
        &mut self, scope: &ScopeId, tick: u64, task: T,
    ) -> Result<TaskId, T>;
    pub fn cancel_scope(&mut self, scope: &ScopeId) -> Option<usize>;
    pub fn cancel_scope_with(
        &mut self, scope: &ScopeId, cancel: impl FnMut(TaskId, T),
    ) -> Option<usize>;
}
```

Existing structs' public construction/exhaustive enums are unchanged. No new
public error enum, iterator type, serializer, format or dependency was needed.
Private task metadata stores a compact slot/generation key, not an Arc per job.
The Arc allocation is shared by that scheduler and caller-held handles. Capacity
limits count jobs and slots, not arbitrary payload bytes or caller-held clones.

## Required registration and consumer handoff

**Required root/module/manifest registrations or reexports: none.**
`crates/ferravex-engine/src/lib.rs` already contains `pub mod scheduler;`.
The existing `pub use ferravex_engine::*;` in `crates/ferravex/src/lib.rs` exposes
qualified `ferravex::scheduler::{ScopeId, TickScheduler}` paths without another
reexport. No new prelude/root convenience export is required. Cargo discovers
`tests/journey400_207.rs` automatically. Parent owns facade/platform validation.

The module-level rustdoc is an actual compiled/executed first-party delayed-
respawn recipe using only `ferravex_engine` imports. It creates a round scope,
executes task 201 `GameSession::advance_batch(...).ticks()` contexts, accepts a
simulated death at absolute tick 1, schedules a respawn at checked tick 3 and
asserts that it runs only at tick 3. It checks zero-tick/catch-up behavior, manual
paused stepping at tick 4 and cancellation before session restart. It reuses the
scope slot, proves the old handle cannot schedule/cancel new-round jobs, and
executes the new round's tick 1. It never reads the batch-end session counter as
an individual tick ID. The second runnable rustdoc retains cancelled payloads
in caller storage; the third new doctest rejects mutable callback reentry.

For the parent-selected real delayed-spawn/respawn consumer: retain one ScopeId
per round/scene/actor lifecycle; schedule from accepted simulation events using
`context.tick.checked_add(delay)` and an explicit exhaustion policy; drain only
inside actual executed contexts; emit spawn feedback only after accepted spawn
work. Cancel that lifecycle before despawn/round replacement/clock reset, then
acquire a fresh scope. Normal reschedule/cancel methods work on member TaskIds.
A local menu must continue network/replay authoritative contexts while suppressing
player commands; the recipe's pause/manual stepping is a single-player inspector
example. No concurrently owned demo was edited. Parent chooses actual adoption.
